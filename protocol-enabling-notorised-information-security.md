## Overview

**Protocol Enabling Notarised Information Security** is to secure, attested data creation by a third party (Customer) for submission back to the issuing party (Originator).

It is **not** a key exchange protocol. Its purpose is to:

- Allow an Originator to issue a trusted, self-validating instrument to a Customer
- Allow the Customer to create data (a Payload) within that instrument
- Allow the Customer to submit the Payload back in a form only the Originator can decode
- Allow the Originator to verify the instrument was genuine and untampered upon return

---

## Parties

| Party | Role |
|-------|------|
| **Originator** | Issues the instrument, shares validation material, receives and verifies the submission |
| **Customer** | Receives the instrument, creates the Payload, submits back to the Originator |

---

## Core Components

| Component | Description |
|-----------|-------------|
| **E** | Workspace ROM — randomly generated by the Originator; the root instrument |
| **S** | Self-signature — produced by encoding E using E as its own ROM: `S = UNSIGNAL(E, ROM=E)` |
| **Base ROM** | A previously shared or public ROM used to wrap the package for transport |
| **Payload** | The data created by the Customer within the instrument |
| **Closed Channel** | A verifiable channel used by the Originator to share S with the Customer independently |

---

## Protocol Steps

| Step | Actor | Action | Purpose |
|------|-------|---------|---------|
| 1 | Originator | Generate random workspace ROM E | Create the secret workspace instrument |
| 2 | Originator | Encode E using E as ROM → produces S: `UNSIGNAL(E, ROM=E)` | Create self-signature; S is the byproduct of E encoding itself |
| 3 | Originator | Encode S and E using previously shared or public Base ROM; set first 2 bytes as indirection offset pointing to S after E | Package S and E for transport; offset allows Customer to locate S within the structure |
| 4 | Originator | (Optional) Share S with Customer via a verifiable closed channel | Enable external validation; implicitly binds instrument to Customer identity |
| 5 | Originator | Wrap S and E inside UNSIGNAL using Base ROM | Package for transport |
| 6 | Originator | Send package to Customer | Deliver the instrument |
| 7 | Customer | Receive package, decode with Base ROM → extract S, E | Access components |
| 8 | Customer | Use first 2 bytes (indirection offset) to locate S after E | Navigate to S within the structure |
| 9 | Customer | Validate E internally: decode S using E → must equal E | Prove E is self-consistent: `UNSIGNAL_decode(S, ROM=E) == E` |
| 10 | Customer | (Optional) Validate S against closed channel copy | Prove E originated from Originator |
| 11 | Customer | Overwrite S location with Payload (P) (encoded with S as the ROM) | Destroy the signature; S is consumed |
| 12 | Customer | Overwrite first 2 bytes with random values | Remove indirection offset; prevent Payload location being determined by an attacker |
| 13 | Customer | Send modified package to Originator | Deliver the submission |
| 14 | Originator | Validate E against Originator's original kept copy of E | Confirm instrument is authentic and untampered |
| 15 | Originator | Extract and decode Payload from restored structure | Extract the Customer's submitted data |

---

## Notes

This protocol does not assume NONCE or timing, if these are required, encode the NONCE inside E, and timings inside E and P. In fact anything can be within E and P as per the use case requirements.

## User-Facing Flow (Automated)

From the perspective of either party, the protocol reduces to 3 steps:

| Step | Actor | Experience |
|------|-------|------------|
| 1 | Originator | Issues the instrument (automated) |
| 2 | Customer | Creates data and submits (automated) |
| 3 | Originator | Receives and validates the submission (automated) |

All 15 protocol steps execute invisibly in the background.

## Security Properties

| Property | How Achieved |
|----------|-------------|
| **E is self-validating** | E encodes itself to produce S; any tampering with E breaks this relationship (step 9) |
| **E integrity on return** | Originator validates E against their kept copy upon receipt (step 16) |
| **S is single-use** | S is consumed by the Customer (step 11); never forwarded |
| **Payload confidentiality** | Entire package re-encoded with S (step 13); attacker has no offset and no S |
| **Forward secrecy** | S is destroyed after use; cannot be recovered from the transmitted package |
| **Customer identity binding** | Only the genuine Customer holds S from the closed channel; a fake party's submission would fail decoding at step 15 |
| **Tamper evidence** | Indirection offset is poisoned (step 12); offset points to random data on return |
| **Non-repudiation** | Originator cannot deny issuing E and S; Customer cannot deny using the instrument |

## Known Weaknesses and Considerations

| Weakness | Notes |
|----------|-------|
| **Closed channel definition** | The mechanism for sharing S (step 4) is external to the protocol and currently undefined; it is the single most critical dependency if you care about proof of originator (could be a pre-arranged B2B channel encoded with UNSIGNAL) |
| **Replay protection** | No timestamp or nonce is defined; a genuine Customer could potentially resubmit a captured package |
| **E expiry** | No built-in instrument lifetime or rotation mechanism is defined |

## Relation to Existing Concepts

The protocol shares properties with several known cryptographic concepts but is not equivalent to any single one:

| Concept | Similarity | Difference |
|---------|------------|------------|
| Redactable Signatures | Authorised modification of signed data | NDS consumes the signature rather than preserving it |
| Chameleon Signatures | Message replacement with valid original signature | NDS uses structural indirection rather than mathematical trapdoors |
| Forward Secrecy | Past sessions unrecoverable after key destruction | NDS achieves this via S consumption rather than key rotation |
| Notarised Documents | Trusted instrument issued, used, returned | NDS embeds the notarisation within the instrument itself |
| Commit-Reveal | Commit to a value, reveal later | NDS commits to E via S, then reveals Payload in place of S |

## Terminology

| Term | Definition |
|------|------------|
| **UNSIGNAL** | The encoding mechanism used throughout this protocol |
| **ROM** | Read-Only Memory — the lookup table used by UNSIGNAL for encoding/decoding |
| **Indirection** | A pointer or offset that references a location rather than containing data directly |
| **Proof of Change** | The underlying mechanism; the authorised, validated replacement of S with Payload is itself the proof |
| **Notarised Data Submission** | The purpose and name of the protocol as a whole |
